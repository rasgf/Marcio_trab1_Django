Biblioteca · Prova P1 · Django

Da URL ao HTML

O caminho completo de uma requisição no projeto Biblioteca, e onde exatamente as duas features da P1 (busca com filtro e validação customizada) entram nesse caminho.

O mecanismo

O navegador manda uma única requisição. O urls.py decide, só pelo endereço e pelo método (GET ou POST), qual das duas rotas abaixo ela segue. As duas rotas sempre terminam devolvendo HTML de volta, só que o que acontece no meio é bem diferente.

Feature 1: Busca e Filtro

Tudo acontece dentro da função lista_livros, em acervo/views.py. Nenhuma dessas linhas é mágica do Django, é lógica comum de filtrar uma lista, só que descrita pro banco de dados executar em vez de rodar um for em Python.

acervo/views.py
  1. def lista_livros(request):
  2. nome = request.GET.get('q', '').strip()
  3. tipo = request.GET.get('tipo', '')
  4. categoria = request.GET.get('categoria', '')
  6. filtro = Q()
  7. if nome:
  8. filtro &= Q(titulo__icontains=nome) | Q(autor__icontains=nome)
  9. if tipo:
  10. filtro &= Q(tipo_acervo=tipo)
  11. if categoria:
  12. filtro &= Q(categoria=categoria)
  14. livros = Livro.objects.filter(filtro)
L9-11

request.GET.get('q', '') pega o valor que veio na URL /livros/?q=machado, que chega pro Django como um dicionário de pares chave-valor. O segundo argumento ('') é usado quando a chave não existe, pra não precisar checar isso na mão.

L18-24

Q() guarda uma condição lógica numa variável, em vez de aplicá-la na hora. Isso é necessário aqui porque a busca por texto precisa de OU (título OU autor), e a forma simples de filtrar do Django (filter(campo=valor)) só sabe fazer E. O &= vai encaixando cada novo critério preenchido com E na condição toda; se um filtro não foi preenchido, ele simplesmente não entra.

L27

Livro.objects.filter(filtro) é o equivalente a pedir "dessa lista de livros, me devolva só os que batem com essa condição". O SQL de verdade (um SELECT ... WHERE ...) só é montado e executado quando o resultado é realmente usado lá no template.

Feature 2: Validação Customizada

Aqui a lógica mora em acervo/forms.py, dentro do formulário que já é gerado automaticamente a partir do model Livro. O Django chama esse método sozinho, não existe nenhuma linha no projeto que diga clean_ano() explicitamente. É uma convenção de nome: qualquer método clean_<campo> dentro do formulário é chamado durante a validação.

acervo/forms.py
  1. def clean_ano(self):
  2. ano = self.cleaned_data.get('ano')
  3. ano_atual = timezone.now().year
  4. if ano and ano > ano_atual:
  5. raise forms.ValidationError(
  6. f'O ano de publicação não pode ser posterior a {ano_atual}.'
  7. )
  8. return ano
nome do método

clean_ano não é chamado por nenhuma linha do nosso código, é o Django que procura, durante form.is_valid(), por um método com esse nome exato (clean_ mais o nome do campo) e o executa sozinho. É o mesmo princípio de convenção sobre configuração que faz o startapp gerar arquivos com nomes fixos.

L13-14

self.cleaned_data.get('ano') é um dicionário com os valores já convertidos pro tipo certo (aqui, ano já é um int, não uma string vinda do input). timezone.now().year é só o ano atual de verdade.

L15-18

raise forms.ValidationError(...) é igual a lançar uma exceção em qualquer linguagem: interrompe o fluxo normal e carrega uma mensagem. O Django captura essa exceção automaticamente, marca o campo ano como inválido e guarda a mensagem, que {{ form.as_p }} (no template) já sabe exibir do lado do campo, sem nenhum código extra nosso.

L19

return ano é obrigatório: todo método clean_<campo> precisa devolver o valor de volta (validado ou não), senão o Django assume que o campo virou vazio.

Uma correção

Na explicação anterior (e no comentário que ficou no código), eu disse que combinar os três filtros num único Q() evitava fazer uma consulta ao banco por filtro. Isso estava errado: o QuerySet do Django é lazy. Encadear .filter() várias vezes só empilha condições, sem tocar o banco, e o SQL só roda uma vez, quando o resultado é de fato usado. Pra três critérios simples como os nossos, sem relacionamento entre tabelas, .filter() encadeado e um Q() combinado geram exatamente a mesma consulta.

O motivo real de precisar do Q() é outro, e está explicado na seção da Feature 1 acima: é a única forma de escrever OU dentro de um filtro. Corrigi o comentário no código e registrei isso num commit à parte.

Para o parágrafo do relatório da P1

O enunciado pede um parágrafo curto justificando o campo/categoria escolhido na Feature 1 e a regra escolhida na Feature 2, e o porquê de cada uma. Aqui está o que já ficou decidido e implementado.

Feature 1

Busca por título e autor (texto livre) combinada com filtro por categoria (as 10 classes do acervo) e por tipo de acervo. Escolhi título e autor porque é o que uma pessoa realmente lembra ao procurar um livro numa biblioteca, ninguém busca pelo ID interno do registro. Categoria virou o filtro principal por ter subconjuntos com significado real (10 classes fixas), diferente de um campo booleano como disponível, que só tem dois estados.

Feature 2

Validação de que o ano de publicação não pode ser posterior ao ano atual. A checagem automática do Django garante só que o campo é um número inteiro preenchido, ela não sabe nada sobre o significado desse número. Sem essa regra, o sistema aceitaria cadastrar um livro com ano 3000, o que não faz sentido: o item já precisa existir, ter sido publicado, para poder ser catalogado. É uma regra de negócio do domínio, não de tipo de dado, por isso só um clean_ano() escrito à mão resolve.
